# Docker Containerization Reflection

When containerizing the application, I made specific choices for the component. For the base image, I selected node:20 (full image) rather than node:18-alpine. Even though the alpine offers lightweight sizes, I discovered that several npm dependencies in my project are not compatible with the environment. Although it was larger, it provided the necessary tools and allowed the project to build successfully. This experience taught me that reliability and compatibility can sometimes be more important than optimisation.

For the service architecture, I used docker-compose.yml to separate the MongoDB database and Node.js application into two services. This made the application easier to manage, and helped to understand how containers communicate through Docker's internal network. I also organised the Dockerfile so that the npm is installed before copying the application code. Through this approach, it allows Docker to use layer caching, which reduces the build time when only the application code changes. For configuration, I used .env to keep the database credential outside the codebase. Beside that, I also use a named volume to make sure the database remains available even after the container restarted.

The first issue I encountered was Node.js compatibility, because some of the dependencies in my project did not work with the lightweight node 18-alpine. To resolve this, I upgraded to Node 20 and resolved the problem. The other issues are the MongoDb authentication. At first, the application can not connect to the database because the authentication configuration is incomplete. So I resolve this by setting the mongoDB credentials through environment variable and updating the URI with ?authSource=admin.

I also experience port conflicts because the port that I want to use (port 3000 and 27017) is still being used by the previous containers. So I ran docker-compose down -v and checked the ports to resolve the issue. Beside all of the challenges I have encountered above, the other challenge for me was the backend of the group project was initially non-functional because it was still in development. This condition means the form could not save and view the data. To resolve this I had to build the controllers, router, API endpoints, and frontend fetch() calls to create an end to end data flow between the user interface backend and MongoDB.

The most challenging part for me was ensuring that the application worked consistently across environments which are my local machine and Docker. When I run the application it might be running as I expected, but several issues appeared after containerisation. I had to understand Docker networking, service names, environment variables, port management, and service dependencies. Each issue gives me the experience and understanding of creating applications that can work not only in my local machine, but also across different environments.

The most rewarding aspect was finally achieving consistency between both environments. After verifying that the application worked locally, I ran docker-compose up and confirmed that the same functionality also worked inside docker. Reports were successfully created and stored, and the data could be displayed correctly. Seeing this application work consistently in both environments was satisfying, because it showed me that the application is working across systems and not dependent on my local setup. Overall this experience taught me that Docker is not just a tool to run containers, but it is an important way to create an application that is reliable, portable, and ready to deploy across systems.
